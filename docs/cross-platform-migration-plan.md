# 跨平台共享 UI 与业务架构迁移方案

日期：2026-09-29。状态：P0 基线与首批契约已形成，业务迁移尚未实施。

当前执行资料：[P0 功能与数据差异](migration-p0-baseline.md)、[管理器桥接契约 v1](manager-bridge-v1.md)。契约仍需在 P1 落实运行时校验和平台验证。

## 1. 目标与边界

以 **Windows 当前管理器界面为基准**，建立一套共享前端、共享业务核心和共享换肤运行时，由 Windows/macOS 原生壳承载。统一功能与业务语义，同时保留必要的系统差异。

本方案覆盖功能清单、代码归属、迁移顺序和阶段完成条件；具体接口字段与实现细节在相应阶段补充。文档落盘不代表已完成迁移，也不代表已授权删除旧实现、修改用户数据或发布版本。

- 共享前端采用 React + TypeScript + Vite，构建为离线静态资源。
- Windows 保留 WPF 宿主，加入 WebView2；macOS 保留 AppKit 宿主，加入 WKWebView。
- 本地业务核心采用 TypeScript，使用随应用分发的 Node.js；现有可复用 JavaScript 模块可以直接接入，不要求先全部改写语言。
- 前后端分离指桌面应用内部职责分离，不增加云端后端，不默认启动本地 HTTP 服务。
- 采用单仓库、模块化架构，不引入微服务，也不为每个业务动作创建独立包。
- 首轮不重新设计产品、不改变主题存储位置、不升级主题格式、不替换平台更新信任机制。后续需要改变这些行为时单独提出兼容方案。

## 2. 当前代码与主要问题

| --- | --- | --- |

| Windows 素材与主题包 | `src/PreviewImageLoader.cs`、`ThemePackageService.cs`、`ThemeCategories.cs` | 缩略图、格式校验、包读写、分类；移到共享媒体/主题包服务与前端显示层 |

| macOS 宿主与业务编排 | `AppDelegate.swift`、`ScriptRunner.swift`、`BoundedCommunityHTTPClient.swift` | 菜单栏、窗口、更新、社区下载、导入恢复、引擎安装等混合；只保留系统集成，业务逐步下沉 |

| macOS 后端 | `manager-actions-macos.sh`、`gui-library.sh/.mjs`、`gui-package.mjs`、`list-manager-themes-macos.mjs` | 已有操作契约与独立 GUI 主题库入口，但不是 Windows 后端的完整等价实现；整合为一个业务入口 |
| macOS 生命周期与事务 | `switch-theme-macos.sh`、`start/pause/restore-dream-skin-macos.sh`、`recover-theme-imports-macos.sh`、`injector.mjs` 等 | 切换锁、暂存发布、恢复和平台引擎控制；保留语义后逐块共享 |
| 已共享运行时 | `runtime/`、`tools/selectors.json`、`tools/sync-runtime-assets.mjs` | renderer、CSS、媒体与 Safe CSS/主题包校验已有单一源；继续复用，不能退回手工维护两份 |
| 发布与安装 | `build.ps1`、`windows/installer/`、`macos/scripts/build-*.sh`、`.github/workflows/` | 两端编译、内置 Node、安装包和更新附件；增加共享产物构建，保留各平台安装链路 |

当前已共享的 renderer/CSS 是注入 **Codex 客户端**的换肤实现，不是管理器前端。两者需要明确分开，避免共享 UI 与注入代码相互依赖。

主要待解决问题：同一业务多语言重复实现；页面和宿主持有流程决策；模型混入 UI 类型；两端状态、错误和能力表达不同；平台脚本与公共运行时边界不清晰。目录搬迁本身不能解决这些问题。

## 3. 目标结构与依赖

建议目录如下；先按模块建立边界，再随功能迁移移动文件，不立即批量重命名现有目录。

```text
ui/                         共享页面、组件、草稿状态、样式、国际化
contracts/                  DTO、命令、事件、错误码、协议版本及运行时校验
core/                       主题库、主题包、媒体、应用编排、恢复、更新策略
  ports/                    存储、平台进程、原生交互、更新安装等能力接口
runtime/                    公共 injector/watcher、renderer、CSS、校验器
platforms/
  windows/                  Windows 路径、进程、脚本及平台实现
  macos/                    macOS 路径、进程、脚本及平台实现
hosts/
  windows/                  WPF + WebView2、单实例、原生桥接
  macos/                    AppKit + WKWebView、菜单栏、原生桥接
assets/                     管理器资源与可共享的预设源
tools/                      资源生成、同步、开发工具
packaging/                  共享产物组装与平台打包入口
docs/                       契约说明、兼容记录和迁移进度
```

`core/` 初期按主题库、主题包、媒体、皮肤控制、更新划分内部模块，不建立过度通用的框架。

```text
共享 UI ── contracts ──> 原生桥接 ──> Node 本地业务核心
                                         │
                              ┌──────────┴──────────┐
                          共享运行时          core/ports
                                                   │
                                          平台适配与原生能力
```

依赖约束：

- UI 仅调用类型化客户端，不导入 Node、平台脚本或本机路径操作。筛选、未保存草稿和预览属于前端；删除许可、校验和提交规则属于业务层。
- `contracts/` 不依赖 React、WPF、SwiftUI 或 Node 特有类型；原生桥接也必须按契约校验，不依赖 TypeScript 编译期类型代替输入检查。
- 核心通过能力接口调用平台实现，不依赖宿主控件。组合入口负责连接核心和具体适配器。
- 壳负责窗口、菜单栏/托盘、系统交互和消息转发；菜单操作与窗口操作走同一业务入口。
- 公共 injector/watcher 不依赖管理器 UI。renderer 在 Codex 页面内运行，与 Node 代码分开构建。
- 主题包和媒体校验只保留一个权威实现；核心及运行时可共同复用纯校验模块，不互相复制。

## 4. UI 基准及完整功能迁移清单

共享 UI 保留 Windows 的“控制台 / 导入图片 / 主题设置”三个主页面，沿用主题卡片、筛选区、预览区、操作区、状态和底部消息的布局关系、配色与操作层级。基准来源是 `src/MainWindow.cs` 和 `ManagerControlStyles.cs`；`docs/screenshots/` 仅作辅助参考，历史截图与当前源码冲突时以当前功能为准。

允许平台标题栏、系统字体、文件对话框和快捷键不同。macOS 已有额外功能放入对应页面或原生菜单，不能为了统一界面静默删除。下表是迁移范围，不表示每项目前两端都已实现。

## 5. 业务和运行时的迁移去向

| 业务模块 | 主要来源 | 迁移方式 |
| --- | --- | --- |
| 主题模型、分类与参数 | `Models.cs`、`ThemeCategories.cs`、Swift 主题模型、`theme-config.mjs`、`gui-library.mjs` | 提取无 UI 依赖的模型及规则；显示标签与磁盘分类 ID 分离，不直接重写旧分类 |

| 应用与恢复流程 | `MainWindow` 的 Apply/Enable/Pause/Restore 编排、`DreamSkinService`、Mac AppDelegate 与切换脚本 | 移入核心用例；把选择主题、保存成功和实际渲染成功区分开，UI 不再拼接脚本流程 |

| 社区与更新 | `apply-community-theme*`、Mac AppDelegate/HTTP client、`check-update*`、`gui-update*` | 公共解析和编排进核心；下载来源、签名、校验、安装权限与平台恢复不削弱 |
| 原生与脚本执行 | `App.cs`、`PowerShellRunner.cs`、`ScriptRunner.swift`、AppDelegate 的系统代码 | 进入壳或平台适配；脚本仅保留必要平台操作和过渡兼容入口 |
| 资源与构建 | 两端 presets/catalog、assets、runtime 同步工具、构建及 release 脚本 | 确认预设 ID/资源差异后建立单一源；共享前端/核心/runtime 先构建，再组装各平台包 |

抽取优先复用已经共享的 `.mjs` 和成熟的 Mac Node 实现，但以行为对照为准，不把“已用 Node”视为正确性证明。旧脚本未迁完前可以作为适配器后端；同一能力切换后只允许一个实现负责写入。

## 6. 统一契约与进程边界

采用“原生壳承载前端 + 随壳启动的 Node 业务进程”。前端通过 WebView 桥接发起类型化操作，宿主通过标准输入/输出的结构化消息与 Node 通信；stdout 只传协议，日志走 stderr。壳与核心间的原生能力请求使用独立消息类型，避免与前端命令混用。

第一批命令按功能分组：

- `status`：状态快照、版本与能力查询、订阅变化。
- `themes`：列表、详情、创建、编辑、另存、删除、批量导入、主题包导入导出、素材保存。
- `skin`：应用、暂停、继续、重置、恢复、连接检查与修复。
- `community`、`updates`、`maintenance`：社区导入、更新查询/执行、平台维护。
- 原生交互：选择/保存文件、打开外部链接、系统通知等，由受限的宿主接口提供。

契约需包含请求 ID、协议版本、操作 ID、结果/错误码和进度事件。长任务不能依赖 WebView 一次回调保持存活；重开页面应能重新获取状态。副作用请求不能因超时自动重发，需先查询操作结果。写操作串行或按资源加锁，保留跨进程锁以覆盖旧 CLI/菜单入口。

状态至少区分用户期望、引擎健康、renderer 结果、进行中的操作；按钮可用性由核心提供，执行时仍重新校验。需要重启或永久删除时返回明确的确认要求，用户确认只绑定本次操作，不能转化成后续无限授权。

管理器业务进程与持续注入 watcher 的生命周期分离：关闭管理器不应意外卸载皮肤或停止原有持续注入；重开时重新读取事实。Node 业务进程异常退出时显示不可用并恢复连接，不能把未返回的写操作直接当成失败重做。

只加载随包分发的管理器页面；外部网页交给系统浏览器。桥接使用命令白名单，不暴露通用 shell 执行。素材通过受限资源 URL/句柄访问，不开放整个磁盘；原生文件选择结果必须经过路径与格式校验，媒体字节不通过大体积 JSON/Base64 来回传递。WebView2 与 WKWebView 的资源加载、视频封面和编码差异在首个闭环阶段确认。

## 7. 数据与兼容底线

1. 首轮不搬动用户主题库，不改变活动主题、暂停标记、状态记录、备份和删除标记的位置；新增仓储适配现有布局。
2. 保持 `theme.json`、`.cdskin` formatVersion 1、Safe CSS 与许可证兼容。导入导出处理 `palette.accent`/`colors.accent` 映射；缺省焦点与显式居中、取景开关和默认不透明度不能被错误归一化。
3. 先记录两端实际字段、默认值、校验限制和未知字段处理，再确定共享规则；有冲突时增加兼容读取，不静默丢字段或批量改数据。
4. 保留暂存校验后发布、原子替换、乐观并发检查、切换锁、失败回滚和中断恢复。内置主题修复不能覆盖用户编辑或复活已删除预设。
5. 主题包路径穿越、符号链接/reparse point、重复条目、解压大小、Safe CSS、媒体解码、下载来源及签名等已有保护均属于迁移功能。
6. “重置默认主题”与“恢复原始外观”保持独立；watcher 存活不等于渲染成功，文件保存成功不等于换肤成功。状态语义参考 [现有状态链路](skin-state-lifecycle.md)。
